01 FUNDAMENTOS

Por que a normalização importa?

Quando um banco de dados cresce sem uma estrutura bem definida, a mesma informação pode aparecer repetida em várias linhas. Isso dificulta a manutenção e aumenta a possibilidade de inconsistências.

A normalização é um processo de organização das tabelas que reduz redundâncias e ajuda a manter os dados corretos. Ela organiza as informações em estruturas relacionadas de acordo com suas dependências.

＋

Anomalia de inserção

A estrutura da tabela pode dificultar o cadastro de uma informação sem que outros dados desnecessários sejam registrados junto dela.

⟳

Anomalia de atualização

Uma informação repetida precisa ser alterada em vários lugares, aumentando o risco de divergências.

⌫

Anomalia de exclusão

Apagar um registro pode remover, por acidente, outra informação que deveria ser preservada.

02 CONCEITO

O que é normalização?

Normalizar significa aplicar regras de modelagem para organizar atributos em tabelas, estabelecer relacionamentos e evitar que o mesmo fato seja armazenado de maneira desnecessariamente repetida.

As formas normais são etapas progressivas. Cada uma estabelece condições específicas para a organização dos dados. Entre as mais estudadas estão a primeira, a segunda e a terceira formas normais, a forma normal de Boyce-Codd, a quarta e a quinta formas normais.

Ideia central

Cada informação deve ser armazenada no lugar adequado e cada tabela deve representar um assunto bem definido.

03 PRIMEIRA E SEGUNDA FORMAS NORMAIS

Organizando os dados em etapas

1FN

Primeira Forma Normal

Uma tabela está na primeira forma normal quando cada campo contém um único valor e não existem grupos repetidos de colunas.

ANTES DA NORMALIZAÇÃO Não recomendado
ID aluno Nome Disciplinas
01 Ana Banco de Dados, Programação
02 Caio Redes, Banco de Dados

Problema: o campo Disciplinas armazena vários valores na mesma célula.

DEPOIS DA NORMALIZAÇÃO Valores atômicos
ID aluno Nome Disciplina
01 Ana Banco de Dados
01 Ana Programação
02 Caio Redes
02 Caio Banco de Dados
2FN

Segunda Forma Normal

Para estar na segunda forma normal, uma tabela deve estar na primeira forma normal e todos os atributos que não fazem parte de uma chave candidata devem depender da chave inteira, e não somente de uma parte de uma chave composta.

Exemplo: matrícula de alunos em cursos

Considere uma tabela cuja chave primária é formada por ID do aluno + ID do curso. O nome do aluno depende apenas do ID do aluno, enquanto o nome do curso depende apenas do ID do curso. Isso caracteriza dependências parciais.

ANTES · DEPENDÊNCIAS PARCIAIS Não está na 2FN
ID aluno ID curso Nome do aluno Nome do curso Nota
01 C01 Ana Banco de Dados 9,0
01 C02 Ana Programação 8,5
02 C01 Caio Banco de Dados 7,5

A chave composta identifica cada matrícula, mas os nomes do aluno e do curso dependem apenas de partes dessa chave.

DEPOIS · TABELA ALUNOS Dados separados
ID aluno (PK) Nome do aluno
01Ana
02Caio
DEPOIS · TABELA CURSOS Dados separados
ID curso (PK) Nome do curso
C01Banco de Dados
C02Programação
DEPOIS · TABELA MATRÍCULAS Relacionamento preservado
ID aluno (FK) ID curso (FK) Nota
01C019,0
01C028,5
02C017,5
O que mudou?

Os dados foram divididos em Alunos, Cursos e Matrículas. A nota permanece em Matrículas porque depende da combinação entre aluno e curso.

04 TERCEIRA FORMA NORMAL

Eliminando dependências transitivas

3FN

Terceira Forma Normal

A terceira forma normal exige que a tabela esteja na segunda forma normal e que os atributos que não fazem parte de uma chave não dependam transitivamente de uma chave candidata.

Exemplo: funcionários e departamentos

ANTES · DADOS REPETIDOS Não está na 3FN
ID funcionário Funcionário ID departamento Departamento
01AnaD01Financeiro
02CaioD01Financeiro
03BrunaD02Recursos Humanos

O nome do departamento depende do ID do departamento, e não diretamente do ID do funcionário.

DEPOIS · FUNCIONÁRIOS Tabela organizada
ID funcionário (PK) Funcionário ID departamento (FK)
01AnaD01
02CaioD01
03BrunaD02
DEPOIS · DEPARTAMENTOS Tabela relacionada
ID departamento (PK) Nome do departamento
D01Financeiro
D02Recursos Humanos
Resultado

O nome de cada departamento fica armazenado uma única vez na tabela Departamentos. A tabela Funcionários referencia o departamento por meio de uma chave estrangeira.

05 FORMA NORMAL DE BOYCE-CODD

BCNF ou 3.5FN

BCNF

Boyce-Codd Normal Form

A forma normal de Boyce-Codd (BCNF) também conhecisa como 3.5FN é mais rigorosa que a terceira forma normal. Para cada dependência funcional não trivial X → Y, X deve ser uma superchave da relação.

Uma superchave é um conjunto de atributos capaz de identificar unicamente cada registro. A BCNF ajuda a eliminar determinadas redundâncias que ainda podem existir em tabelas que atendem à terceira forma normal.

Exemplo: professor, disciplina e sala

Considere as regras de um sistema acadêmico: cada professor utiliza uma única sala, e a combinação de professor e disciplina identifica uma atribuição.

ANTES · SALA REPETIDA Dependência problemática
ProfessorDisciplinaSala
MarcosBanco de DadosSala 10
MarcosProgramaçãoSala 10
HelenaRedesSala 20

A regra Professor → Sala indica que o professor determina a sala, mas Professor não é superchave da tabela original.

DEPOIS · PROFESSORES Dependência separada
Professor (PK)Sala
MarcosSala 10
HelenaSala 20
DEPOIS · ATRIBUIÇÕES Relacionamento preservado
Professor (FK)Disciplina
MarcosBanco de Dados
MarcosProgramação
HelenaRedes
Atenção

O exemplo pressupõe que cada professor utiliza uma única sala. As dependências e as chaves precisam corresponder às regras reais do sistema.

06 QUARTA FORMA NORMAL

4FN: eliminando dependências multivaloradas

4FN

Quarta Forma Normal

A quarta forma normal exige que a tabela esteja na BCNF e que não existam dependências multivaloradas não triviais, exceto quando o determinante for uma superchave.

Esse problema aparece quando uma entidade possui dois ou mais conjuntos independentes de valores. A combinação desses conjuntos pode gerar linhas redundantes sem representar uma relação real entre eles.

Exemplo: alunos, idiomas e hobbies

Imagine que Ana fale dois idiomas e pratique dois hobbies. Os idiomas e os hobbies são independentes: praticar natação não significa que ela fale um idioma específico.

ANTES · COMBINAÇÕES REPETIDAS Não está na 4FN
AlunoIdiomaHobby
AnaInglêsNatação
AnaInglêsLeitura
AnaEspanholNatação
AnaEspanholLeitura

Cada idioma aparece combinado com cada hobby, mesmo sem haver dependência entre essas informações.

DEPOIS · IDIOMAS DO ALUNO Conjunto independente
AlunoIdioma
AnaInglês
AnaEspanhol
DEPOIS · HOBBIES DO ALUNO Outro conjunto independente
AlunoHobby
AnaNatação
AnaLeitura
Resultado

As tabelas passam a representar separadamente os idiomas e os hobbies de cada aluno. Isso elimina combinações artificiais e evita repetir informações sem necessidade.

07 QUINTA FORMA NORMAL

5FN: decomposição sem perda de informação

5FN

Quinta Forma Normal

A quinta forma normal, também chamada de forma normal de projeção-junção, trata de situações em que uma tabela pode ser dividida em tabelas menores e reconstruída por meio de junções, sem perder informações nem criar combinações indevidas.

Ela é especialmente relevante quando existem dependências de junção complexas. A decomposição precisa ser justificada pelas regras de negócio: não basta dividir uma tabela arbitrariamente.

Exemplo: fornecedores, peças e projetos

Imagine uma empresa que registra quais fornecedores fornecem determinadas peças para determinados projetos. Considere a regra de negócio de que uma combinação fornecedor-peça-projeto é válida quando as três relações individuais correspondentes são válidas.

RELAÇÃO ORIGINAL Tabela combinada
Fornecedor Peça Projeto
F01P01J01
F01P02J01
F02P01J02

A decomposição em cinco formas normais só é válida se as regras de junção do domínio garantirem a reconstrução exata da relação original.

RELAÇÃO FORNECEDOR-PEÇA Tabela relacionada
FornecedorPeça
F01P01
F01P02
F02P01
RELAÇÃO FORNECEDOR-PROJETO Tabela relacionada
FornecedorProjeto
F01J01
F02J02
RELAÇÃO PEÇA-PROJETO Tabela relacionada
PeçaProjeto
P01J01
P02J01
P01J02
O ponto mais importante

A 5FN não significa apenas separar tabelas. A decomposição deve preservar exatamente as combinações válidas quando as tabelas são reunidas novamente por junções.

08 ESTRATÉGIA DE MODELAGEM

Desnormalização: quando repetir dados pode ser útil

A desnormalização é uma decisão de projeto que introduz redundância de forma controlada em um banco de dados. Ela pode ser utilizada para reduzir o custo de consultas frequentes, diminuir a quantidade de junções ou melhorar o desempenho de determinadas operações de leitura.

Ao contrário da normalização, que busca organizar os dados e evitar redundâncias desnecessárias, a desnormalização aceita alguma repetição quando existe uma necessidade de desempenho comprovada.

Exemplo: pedidos e nomes de clientes

Em um modelo normalizado, o pedido guarda o identificador do cliente e a tabela Clientes armazena o nome. Para consultar o nome do cliente junto ao pedido, é necessário relacionar as tabelas.

MODELO NORMALIZADO · CLIENTES Dados separados
ID cliente (PK)Nome
C01Ana Souza
C02Caio Lima
MODELO NORMALIZADO · PEDIDOS Chave estrangeira
ID pedidoID cliente (FK)Valor
1001C01R$ 150,00
1002C02R$ 200,00
1003C01R$ 80,00

Em um cenário de relatórios que consultam constantemente os pedidos e o nome do cliente, uma estrutura desnormalizada poderia armazenar também o nome do cliente na tabela de pedidos.

EXEMPLO DESNORMALIZADO · PEDIDOS Nome repetido
ID pedido ID cliente Nome do cliente Valor
1001C01Ana SouzaR$ 150,00
1002C02Caio LimaR$ 200,00
1003C01Ana SouzaR$ 80,00
Vantagem e cuidado

A consulta pode ficar mais simples, mas o nome do cliente fica repetido. Se ele mudar, todas as cópias relevantes precisam permanecer consistentes. A desnormalização deve ser aplicada com justificativa, testes e controle de atualização.

VANTAGEM

Leituras mais rápidas

Pode reduzir junções e acelerar consultas específicas.

RISCO

Mais redundância

Pode aumentar o armazenamento e dificultar atualizações.

09 APLICAÇÃO

Exemplo prático: um cadastro de cursos

Imagine uma tabela que registra matrículas, nomes de alunos, cursos e nomes de instrutores. Se o nome do curso e o nome do instrutor forem repetidos em cada matrícula, uma alteração exigirá mudanças em muitas linhas.

  1. 1
    Identifique as entidades

    Separe aluno, curso, instrutor e matrícula conforme as regras do sistema.

  2. 2
    Defina as chaves

    Escolha identificadores únicos e determine como as tabelas se relacionam.

  3. 3
    Revise as dependências

    Confira se cada atributo depende da chave correta e evite repetir fatos.

  4. 4
    Valide o resultado

    Teste inclusões, atualizações e exclusões para confirmar a consistência dos dados.

10 VANTAGENS

O que melhora com a normalização?

01

Menos redundância

Evita armazenar o mesmo fato repetidas vezes.

02

Mais consistência

Reduz a chance de dados conflitantes após uma alteração.

03

Manutenção clara

Facilita entender as responsabilidades de cada tabela.

04

Integridade melhor

Relacionamentos e restrições ajudam a proteger os dados.

11 CONCLUSÃO

Organizar os dados é construir uma base confiável

A normalização é uma etapa fundamental da modelagem de bancos de dados relacionais. Ela ajuda a estruturar as informações, reduzir redundâncias desnecessárias e evitar anomalias de inserção, atualização e exclusão.

Cada forma normal trata de um tipo de problema. A 1FN organiza os valores em cada campo; a 2FN elimina dependências parciais; a 3FN trata dependências transitivas; a BCNF exige que os determinantes das dependências funcionais sejam superchaves; a 4FN aborda dependências multivaloradas; e a 5FN trata de dependências de junção.

A desnormalização, por sua vez, pode ser útil em cenários nos quais o desempenho de consultas é prioritário. No entanto, ela deve ser adotada de forma consciente, considerando os impactos na consistência, na manutenção e no armazenamento.

✓

Conclusão: não existe apenas a tarefa de dividir tabelas. O objetivo é representar corretamente as regras do negócio, preservar os relacionamentos e escolher uma estrutura que equilibre integridade, manutenção e desempenho.
